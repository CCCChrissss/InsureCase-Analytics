# 本機 BGE 低分查詢改寫分析

## 目的

針對 benchmark v1 中 Strict Precision@5 較低的四個查詢，檢查低分原因，並比較兩種較完整的自然語句改寫是否能改善 Top 5 命中品質。

- 原始查詢：`違反告知義務`、`手術認定`、`業務招攬`、`豁免保費`
- 模型：`BAAI/bge-large-zh-v1.5-local`
- Provider：`local_bge`
- 候選範圍：trial DB 中既有的 1000 筆 BGE embeddings
- 每個查詢：Top 5
- 結果數：12 個查詢版本，共 60 筆
- 判讀方式：Codex AI 輔助判讀；檢查命中 chunk，必要時回查前後相鄰 chunk
- 執行限制：完全使用本機模型快取，未呼叫 Hugging Face API，未修改 SQLite 資料庫

原始執行結果位於 Git 忽略的 `outputs/local_bge_low_precision_query_trial.json`。

## 標記規則

- `relevant`：命中段落直接處理查詢中的主要法律、條款或事實問題。
- `partially_relevant`：涉及相鄰概念，但未直接處理完整查詢意圖。
- `not_relevant`：只有表面詞彙重疊，實際爭點不同。
- Strict Precision@5：只有 `relevant` 計為命中。
- Lenient Precision@5：`relevant` 與 `partially_relevant` 都計為命中。

## 結論與實作建議

1. 四個低分查詢的主要問題不是模型完全無法理解中文，而是二至六字的查詢缺少主體、行為、條件或法律效果。
2. 本次最佳改寫相較原查詢的 Strict P@5：違反告知義務 `0.6 -> 1.0`、手術認定 `0.6 -> 1.0`、業務招攬 `0.6 -> 0.8`、豁免保費 `0.0 -> 1.0`。
3. 不能直接以固定字串取代所有使用者查詢。較安全的產品方向是提供「建議查詢」或讓使用者補充完整問題，並同時保留原查詢結果。
4. 若要自動改寫，API response 應揭露原始查詢、實際送入 embedding 的查詢及改寫規則，前端也要允許使用者切回原查詢。
5. 暫時不建議加入硬性爭議類型 filter。部分真正相關結果的 metadata 爭議類型不同，例如手術認定命中條款解釋或承保範圍案件，硬性 filter 會降低召回率。
6. 暫時不建議切換正式 DB。這次只有四個主題、每個版本 Top 5，且標註為 AI 輔助；仍需第二位獨立標註者與較完整 benchmark 才能作正式品質依據。

## 建議下一個可驗證步驟

先新增「查詢建議規則」的離線測試層，不直接改 production API：

1. 定義短查詢觸發條件與可解釋的建議句型。
2. 擴充到原 benchmark 15 詞，每詞至少一個自然語句版本。
3. 由第二位標註者盲標原查詢與建議查詢結果。
4. 只有在多數查詢不退步、低分查詢穩定改善後，再決定是否於 API 增加可選的 query suggestion / rewrite。
